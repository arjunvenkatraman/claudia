# ADR-004: Guided, per-machine setup via a generated config file

**Status:** Accepted

## Context

The container environment (`containerconf/`) was written for one host: host folders
`~/xpal-src`, `~/xpal-data`, `~/xpal-auth`, UID 501, the `podman` runtime, a fixed port
set, and fixed image/container names were all hardcoded into the run scripts and README.
The `claudia` CLI similarly hardcodes machine-local paths (`~/.claude/...`) for session
logs, snapshots, labels, and taxonomy.

To let a new person stand up the same environment under guidance, every machine-specific
choice must be captured once, in their local copy, without touching the container image
(which stays the source of truth) or committing any personal data.

## Decision

**1. Guided setup wizard.** Add `containerconf/setup.sh` — an interactive script that
prompts for each customization point (with a sensible default) and writes a local
`containerconf/.env`. It creates the host folders and validates the UID. Non-interactive
runs are supported by prefixing env vars (e.g. `XPAL_HOST_SRC=... ./setup.sh --yes`).

**2. Config-driven scripts.** `run-daily.sh`, `run-daily-remote.sh`, `run-ephemeral.sh`,
`build.sh`, and `cleanup.sh` source `.env` and use its variables instead of hardcoded
values. `build.sh` passes `--build-arg HOST_UID=$XPAL_HOST_UID` to the Containerfile
(which already accepts the `HOST_UID` build arg). `.env` is gitignored and never
committed; `containerconf/.env.example` documents every key for review.

**3. CLI path overrides.** `claudia.py` keeps `~/.claude/...` defaults but honors
environment-variable overrides so a machine with non-standard locations (e.g. a mount
point) can redirect session glob, snapshot dir, labels cache, and taxonomy file. Defaults
unchanged — existing installs are unaffected.

**4. Pre-publication cleanup protocol.** Before anything is pushed to a public repo, run
`scripts/scrub-public.sh` (new) and follow `docs/public-release.md` (new). This removes
proper nouns, host paths, usernames, and localhost ports, and enforces that generated
state (`.env`, `.claude/`, `.DS_Store`) is untracked.

**Config keys generated by setup.sh:**

| Key | Default | Purpose |
|---|---|---|
| `XPAL_RUNTIME` | `podman` (auto-detects `docker`) | container runtime |
| `XPAL_IMAGE` | `xpal-claudia` | image name |
| `XPAL_CONTAINER` | `xpal-dev` | day-to-day container name |
| `XPAL_CONTAINER_REMOTE` | `xpal-dev-remote` | day-to-day+remote container name |
| `XPAL_HOST_SRC` | `~/xpal-src` | code working dir (resolved to absolute) |
| `XPAL_HOST_DATA` | `~/xpal-data` | local data (resolved to absolute) |
| `XPAL_HOST_AUTH` | `~/xpal-auth` | all credentials (resolved to absolute) |
| `XPAL_HOST_UID` | `id -u` | host user UID for `--userns=keep-id` |
| `XPAL_PORTS` | `5001:5001 8001:8001 8080:8080` | published ports |
| `XPAL_HOST_REMOTE_DIR` | *(empty)* | optional synced SharePoint folder |

## Consequences

- **One guided step per machine.** After `./setup.sh`, every script matches the local
  filesystem, runtime, and UID. The Containerfile is unchanged as the image source of truth.
- **`.env` must never be committed.** Already covered by `containerconf/.gitignore`
  (`*.env`); the scrub script additionally checks for it before a push.
- **Preserved defaults.** The original host's behavior is reproduced exactly by accepting
  the defaults — so this ADR supersedes the path-rename edits made before it without
  losing them.
- **CLI stays offline-first.** Env overrides are read only; no new network or auth paths.
- **Shared nouns remain internal.** The `xpal` prefix remains as the default for existing
  users but is now a configurable default, not a baked-in constant; the scrub protocol
  makes it trivial to rename for public publishing.
